# 待验证假设与开放问题

更新日期：2026-10-17（Asia/Shanghai）。本文件中的内容均不是平台技术事实。未经带证据的观察，不得据此编写真实页面操作逻辑。

## 使用条件

| 编号 | 待确认事项 | 当前状态 | 验证方式 |
| --- | --- | --- | --- |
| U1 | 目标活动的官方开售日期、时间、时区、场次及参考活动状态 | 两个活动 URL 已提供；用户澄清原开售时间只是模糊记忆，不作为规划依据；官方时间和活动状态待核实 | 以活动官方页面为来源，记录具体时间、时区、适用售票阶段及证据；详见 ALLTICKET_RESEARCH.md |
| U2 | 用户实际运行环境能否打开并操作 Playwright 浏览器 | 用户已选择本地运行；操作系统和实际启动、人工登录仍未验证 | 在用户电脑执行准备流程、启动浏览器并人工登录 |
| U3 | 云端图形桌面是否是本次交付前提 | 用户已选择本地运行，因此不是当前使用前提；开发环境无 DISPLAY，也未配置远程桌面 | 无需为本次本地交付新增云端桌面；后续如改变使用方式再评估 |
| U4 | 平台当前条款允许何种观察和辅助功能 | 未验证 | 查看适用活动及官方说明，不将可访问等同于获准自动操作 |
| U5 | 当前活动是否存在地区、账号、设备或访问限制 | 未验证 | 在用户授权的正常会话中观察；遇限制不绕过 |
| U6 | 参考 URL 末尾分号是否属于链接 | 用户原始输入含末尾 `;`，暂按标点解释并保留原文；规范化地址有效性未验证 | 访问官方页面时验证去除分号的候选 URL；不能把代理连接失败当成页面不存在 |
| U7 | GitHub Draft Release 创建权限及认证状态 | 用户已保存域名配置，但当前实例复检仍为 `allowed_hosts=[]` 且执行限制；`gh api user` 仍返回 Forbidden，认证状态未知 | 待配置在实际执行环境生效后检查连通性与权限；不能推断凭据无效 |
| U8 | 目标活动的购票规则 | 尚未取得官方页面证据 | 核实官方说明中的购买数量限制、身份要求、付款期限及其他适用规则；未披露部分保持未知 |

## ALL TICKET 优先研究；TTM 独立验证

两个平台分别收集证据。同一平台的不同活动也可能采用不同流程，不能直接推广。

| 节点 | 人工正常浏览中的事件 | 研究问题 |
| --- | --- | --- |
| T1 | 进入选座页面 | 页面和可见座位何时加载完成？各计时口径分别耗时多久？ |
| T2 | 用户自行选择座位 | 可见状态如何变化？是否出现官方预订提示？不能仅凭选中样式判断已经锁票 |
| T3 | 用户自行确认选择 | 官方在何时、以何种可见提示确认座位已预订？ |

当前 M2 工具不自动触发 T2/T3。涉及真实占位、确认或支付的研究应在用户自行进行的正常购票过程中观察，不为实验而无意占位。

需要分别验证：

1. 点击座位是否已锁票，还是确认之后才开始预订？
2. 页面显示可用的座位是否可能已经失效，如何从可见界面区分？
3. 正常页面通过什么方式更新可见状态，何时能观察到更新？
4. 不同活动、场次、区域、票档是否使用不同流程？
5. 官方是否提供自动分配座位或无需手工选座的选项？
6. 可见错误、排队、登录失效、验证码和售罄提示有哪些表现？
7. 能否在不收集账号或支付信息的前提下取得足够的状态与耗时证据？

## 研究结论升级规则

- 官方活动页面是开售日程与购票规则的事实来源。用户的模糊回忆不用于设定开售日期、倒计时、提醒或开发截止日；此前相对日期的换算已失去规划依据。
- 取得官方页面内容后，记录来源 URL、读取日期、原文时间和时区、适用售票阶段与规则；再更新计划和说明。无法访问或内容不完整时维持“待核实”。
- 每条观察记录注明平台、活动 URL（脱敏）、日期和时区、人工操作步骤、计时口径、可见证据和局限。
- 可复现的界面现象只能支持相应现象，不自动证明服务端库存或锁票机制。
- 关键词匹配、URL 特征和通用页面分类属于启发式判断；平台专属解析器须另附真实页面证据和适用范围。
- 本地固定页面和模拟器测试只能证明工具行为，不能证明平台行为。
- 新证据先写入对应研究日志；确认需求或工程决策发生变化时，再同步需求、决策和计划。
